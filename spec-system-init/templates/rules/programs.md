# Programs — R.14

> **STOP.** This file applies only if `docs/programs/` has a manifest (work across 2+ SPECs that depend on each other). Covers: the DAG format, derivation of order/`Blocks`, `audit --deps`, `next`. Otherwise the brief/--help answer.

> Read when: work spans 2+ interdependent SPECs, when creating/editing `docs/programs/<slug>.md`, or when `audit --deps` complains.

## What a program is

Program = DAG of SPECs with dependencies. Two ordering levels, zero overlap: the **program orders SPECs**; **tasks order work inside a SPEC**. If the work fits in one SPEC (even size L, with phases), it is NOT a program. A giant feature that does not fit one arc becomes a program: each block becomes its own SPEC.

## Epic/pillar = program (slicing IS creating a program)

Demand too large for a single arc ("epic", "pillar", "slices") is EXACTLY the program case: each slice = its own SPEC (graph node, `**Program:** <slug>`); what remains = `draft` nodes in future/; progress = **derived** (`Ndone/Ntotal` in the generated PROGRAMS.md; `next` points to the next node).

**ANTI-PATTERN (forbidden):** keeping a "container SPEC" forever in `future/` as the epic's umbrella, with progress maintained BY HAND in a prose section (a "slices delivered/remaining" table). That reinvents the program outside the tool: PROGRAMS.md/`next`/brief go BLIND to the real work, the counter freezes, and the manual table is a dual write (violates "derived is never written"). A SPEC is a contract that CLOSES — not a container. A map of "what remains" that does not yet deserve future SPECs is a planning draft (`.scratch/`), never the source of progress.

## Single manifest — `docs/programs/<slug>.md`

The WHOLE graph lives in one file, in main. Literal format — nothing else:

```
# Program: <slug>

**Owner:** @handle

- SPEC-<id> | depends on: —
- SPEC-<id2> | depends on: SPEC-<id>
- SPEC-<id3> | depends on: SPEC-<id>, SPEC-<id2>
```

One line per node. `depends on:` takes `—` (root node) or comma-separated SPEC-ids (PT `depende de:` also accepted). The parser reads ONLY lines of the form `- SPEC-… | depends on: …`. Each participating SPEC's main.md declares only `**Program:** <slug>` (filled by `specctl new <slug> --program <p>` or edited under lint validation) — **no dependency field in main.md**.

## Semantics: derived is never written

`Blocks:` and the topological order are DERIVED from the manifest — never written by hand anywhere (not in the manifest, main.md or features; `audit --deps` warns). "What SPEC-a blocks" = inverted edges. "What can I pick up now" = nodes whose dependencies are all `done`. Writing `Blocks:` by hand is a bug: it was v3's dual write, physically impossible across branches — the single manifest in main kills the root cause.

## Single writer

The manifest lives in main and is edited by a **dedicated PR** (a coordination decision, like the taxonomy) — never from a SPEC branch alongside code. Any dev proposes; the program Owner merges. Completed nodes stay in the manifest (graph history); the program "ends" when every node is `done`/`discarded` — the file stays.

## Validation — `node scripts/specctl.mjs audit --deps`

| Check | Severity |
|---|---|
| Manifest node with no matching SPEC folder | error |
| Dependency that is neither a node nor an existing SPEC | error |
| Cycle in the graph | error |
| Manifest with no node lines / with a written `Blocks` | warning |
| status×DAG coherence: `done` node with a not-yet-`done` dependency | warning |
| status×DAG coherence: `active` node with a `discarded` dependency (edge to re-plan) | warning |

Status comes from each SPEC's main.md (single source); the manifest has NO status field. Activating a SPEC whose dependency is not `done` is not blocked (no CLI check) — `next` lists it as blocked; early unblocking is a negotiation with the depended-on node's Owner (the claim in `docs/claims/` says who). A main.md `**Program:**` naming a missing manifest is not checked by `audit --deps` (only `next --program` rejects an unknown slug) — keep it in sync by hand. The docs-gate runs `audit --deps` on every PR.

## Discovery — `docs/PROGRAMS.md` (generated) and `specctl next`

Defining the graph is not enough; someone must READ the backlog to know the next piece of work — without trawling every manifest. Two pieces close that:

- **`docs/PROGRAMS.md`** is GENERATED by `specctl index` (with INDEX/ARCHIVE-INDEX/DEFERRED; `> GENERATED — specctl index — DO NOT EDIT`). One block per program with **derived** status: `## <slug> — open|done · Ndone/Ntotal · owner` + lines `ready:` / `in progress:` / `blocked: (waits on X)` / `paused:` / `done:` (lists the done nodes — this makes a finished program's block a historical map of its SPECs). O(1) discovery: 1 file shows every program, its next nodes and what it delivered. Labels are NOT stored — recomputed from the real `Status` on every `index`/`next`/brief: closing the dependency moves the node from `blocked` to `ready` BY ITSELF ("pending" = ready + blocked; the split says what is pickable NOW).
- **`node scripts/specctl.mjs next [--program <slug>]`** computes the next work on demand, crossing the graph with the SPECs' real status: **▶ ready** (draft with all deps `done`), **⏳ active**, **🔒 blocked** (with the missing dep). It also reads the ROADMAP and lists the unprioritized backlog (see `lifecycle.md`).

Derived status (never written): program **open** = ≥1 non-`done` node; **done** = all `done`/`discarded`. Node **ready** = `draft` + all deps `done`. The SessionStart **brief** injects the summary (open programs + next node) — the model sees what to pick up when the session opens, without reading the manifests. A finished program is NOT moved or deleted: the manifest stays in `main` as graph history.

## Cross-repo — not implemented by specctl (manual convention only)

specctl has no cross-repo support: a node prefixed with a repo id (e.g. `- back:SPEC-…`) does not match the parser and is silently ignored by `audit --deps`, `index` and `next`; a prefixed id inside `depends on:` is read as a local SPEC-id and fails as a missing dependency. Convention if you need it: one SPEC per repo, each in its own single-repo program with full local enforcement; link them by hand (each program file names the other repo's SPEC-id in prose, outside the node lines). See rules/team.md § Multi-repo.

## Full example (single repo)

```
# Program: billing-v2

**Owner:** @joao

- SPEC-20260701-0900-billing-schema | depends on: —
- SPEC-20260702-1400-billing-api | depends on: SPEC-20260701-0900-billing-schema
- SPEC-20260703-0800-billing-migration | depends on: SPEC-20260701-0900-billing-schema
- SPEC-20260702-1410-billing-ui | depends on: SPEC-20260702-1400-billing-api
```

Derived reading: schema blocks api and migration; api blocks ui. Topological order: schema → (api ∥ migration) → ui. Coherence: if `billing-ui` is `active` while `billing-api` is still `active`, the audit warns — either activation was premature or the edge is wrong; both are resolved by a dedicated PR to the manifest or a conversation with the Owner.
